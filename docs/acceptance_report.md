# Acceptance Report — measured results

> Every number in this report was **measured** by running the real engine against
> the deterministic simulator. Nothing here is a target, an estimate or an
> aggregate "accuracy score". The command that produced each table is given
> beside it, and each value is pinned by a regression test so it cannot drift
> silently.
>
> **Ground truth is synthetic.** This report is evidence that the *pipeline and
> its invariants* are correct on a controlled household, **not** evidence that
> per-device accuracy has been validated in your home. That remains
> **unverified** — see §7.

---

## 1. Scope and configuration

| Item | Value |

| Household | synthetic reference household — **not** a real installation |
| Scenario | seed `202`, 60 simulated minutes, 15 s records |
| Data quality | `good` (impairments still present: dropouts, repeats, stale samples, polarity errors) |
| Topology | two-panel reference topology — 36 power CTs, 37 attributable devices, 2 measurement groups |
| Engine | real `DisaggregationEngine` via `load_engine_predictor`; **no** mock, no stub |
| Records evaluated | 240 |
| Reproduce | `.venv/bin/python -m pytest tests/simulation/test_accuracy.py -q` |

The reference household is generated by `tools/dev/make_reference_house.py` and
committed under `data/examples/reference_house/`. It is structurally identical to
a two-panel multi-CT install (18 channels per panel, dedicated and branch CTs,
double-pole 240 V pairs, one nested sub-feed) but describes no real building.

Stratification is mandatory in this report. There is deliberately no single
aggregate accuracy figure (spec §19.4); `test_no_single_aggregate_score_is_exposed`
enforces it structurally.

## 2. Attribution coverage and safety invariants

| Metric | Measured | Meaning |
| --- | --- | --- |
| Attribution coverage | **0.7031** | fraction of truly-attributable load the engine named |
| Unknown-load share | **0.0247** (2.5 %) | residual left explicitly un-attributed |
| False-attribution rate | **0.0098** (0.98 %) | share of claimed power that was wrong |
| False-attribution power | **142.4 W** of 14 514.4 W claimed | absolute magnitude of the false claims |
| Forced attribution (fabrication) count | **0** | inferred/model power never exceeds the post-direct residual |
| Over-attribution count | **0** | sample-vintage skew on a 3 kW double-pole load; bounded, see §5 |
| Nested double-count records | **0** of 229 checked | sub-panel mains are never added to main-panel mains |
| Stale-learning violations | **0** | nothing was learned from a stale reading |
| Residual preserved ratio | **0.9958** | unknown residual is carried through, not zeroed |
| Residual understated records | **1** of 240 | see §5 |
| Negative-residual records | **1** of 240 | sample-vintage skew, reported not clamped |
| Direct-exceeds-main records | **0** of 240 | same sample-vintage artefact, separate axis |
| Headroom violation records | **0** | inferred power never exceeded the predictor's own remaining headroom |

The coverage gap to 1.0 is entirely the shared-branch devices in §4.3: the engine
leaves them as residual rather than inventing wattages for them.

**Over-attribution is not fabrication.** A dedicated CT sampled one poll interval
earlier still carries the previous ON value when a load switches off, so summed
direct readings can briefly exceed the current panel draw. The invariants keep
this on a separate axis (`negative_residual_records`, `direct_exceeds_main_records`)
from manufactured power (`forced_attribution_count`, which is **0**). Both are
reported, neither is clamped, and the acceptance test bounds them rather than
asserting an impossible zero.

## 3. Error by attribution source

Produced by `tests/simulation/metrics.py::evaluate` over the scenario in §1.
`relative_error` is MAE divided by the mean truth magnitude in that group.

> **Terminology note.** "Source" here is `InferenceResult.source` — *how* a
> value was obtained. It is **not** the `ConfidenceTier` of ADR-0013, which is a
> separate ordered evidence grade reported alongside the value. The two are
> deliberately distinct and must not be conflated in reports.

| Attribution source | n (device-samples) | MAE (W) | RMSE (W) | Mean bias (W) | Relative error |
| --- | --- | --- | --- | --- | --- |
| `direct_measured` | 5 641 | **12.73** | 207.25 | −0.22 | 0.0135 |
| `inferred` | 104 | **1.61** | 11.80 | −1.22 | 0.0287 |
| `unknown` | 3 135 | **468.68** | 1 261.82 | −468.68 | 1.0000 |

Reading these honestly:

* **`direct_measured`** tracks truth closely. Residual error is dominated by
  sample-vintage mismatch (CTs sampled at slightly different instants) and by
  CT quantisation, not by mis-attribution — the bias is −0.22 W.
* **`inferred`** is a small tier (104 samples) because the engine only infers a
  device when it has positive evidence from a state transition plus a step in a
  supporting CT. Its negative bias is deliberate conservatism.
* **`unknown`** has relative error 1.0 *by construction*: this tier is power the
  engine explicitly did not attribute. Its MAE is the size of the unattributed
  load, not an error in a claim. It is the honest cost of the coverage gap.

### 4.3 Shared-branch devices — the documented limitation

Thirteen devices share a branch CT with a sibling and are therefore **not
separable** by this topology. The engine's SVD pre-analysis marks them
`unidentifiable` and reports 0 W in the `unknown` tier. Measured recall is **0**
for every one of them, and **precision is 1.0** (no false ON events):

`washing_machine`, `dishwasher`, `dryer`, `utility_1`, `utility_2`, `utility_3`,
`utility_4`, `workstation`, `laptop`, `monitor`, `printer`, `tv`, `freezer`.

That combination — zero recall, perfect precision — is the *safe* failure. The
alternative (splitting a shared reading by guesswork) is exactly the
"plausible-looking but incorrect" output the spec forbids. This is a
**topology-resolution** limitation, not an inference bug; it is resolved by
adding a per-device CT or a smart plug, not by code changes.

## 7. What this report does **not** establish

Stated plainly, because an acceptance report that overstates its evidence is
worse than none:

1. **No household ground truth.** Per-device accuracy against real appliances is
   **unverified**. The only ground truth available is synthetic. Real-install
   work is limited to a read-only environment audit, an evidence-derived
   state-entity mapping over recorder history, and passive observation; none of
   these provides appliance-level truth. Those audit artifacts are produced
   locally by the tools in `tools/audit/` and are deliberately not committed.
2. **No calibrated confidence.** `confidence_is_calibrated` is `False`
   everywhere (ADR-0007). The `confidence` field is a heuristic score, not a
   probability, and must not be presented as one. The `confidence_tier`
   (ADR-0013) is an **evidence grade**, likewise not a probability, and its
   *accuracy* is unverified: what is proven is that the tier is derived
   correctly from the evidence, not that a tier-4 value is more accurate than a
   tier-3 one in a real household. There is no aggregate accuracy score for
   tiers, by design.
3. **No claim of shared-branch separation.** §4.3 documents that those devices
   are not resolved. This is a known, bounded limitation. A device the user
   declares `shared` with unmodelled siblings is reported as a **configured
   prior** (tier 1), never as a measurement, and the row is held as an upper
   bound with an explicit solver slack.
4. **The topology starts `candidate`.** Learning correctly refuses to train from
   it (ADR-0008) until the user confirms it. The learning *pipeline* is proven
   end-to-end in tests (§8).
5. **Synthetic accuracy is not a performance guarantee.** Simulator impairments
   are modelled on measured audit behaviour, but real installs have effects (RF
   dropouts, integration bugs, firmware drift) that this scenario does not
   reproduce.
6. **No device configuration is applied by default.** Every device starts at
   `unknown` on all three axes. The configuration paths are covered by unit and
   engine tests over realistic topologies, not by live declarations.

These are correctness properties of the production wiring, each with a
regression test that fails if the behaviour is lost:

| Property | Test |
