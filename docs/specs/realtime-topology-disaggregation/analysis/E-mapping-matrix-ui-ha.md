## 3. Reusable assets to keep

- **Honesty rules in `mapping.py`**: `None` (never 0) for unsupported estimates (`:410-437`, `:531-532`); bounds-bracket validator (`contracts.py` `_bounds_bracket_the_estimate`); unknown-load namespaced ids (`:77`, `:611`); `ConfidenceVector` "no blend" discipline (`contracts.py:832-870`), which should be extended rather than replaced; deterministic `stable_json` (`:152`). - **`panel_tree.build_panel_tree`** (`electrical/panel_tree.py:1150`): panel derivation, alias merge and the "Unattributed" group are the right raw material for the L1–L3 column tree. Reuse it via a shared helper rather than through the UI.

- **Async discovery job manager** (`server.py:726-781`, `DiscoveryJobManager`) is a template if a full re-materialisation or reconciliation needs to be API-triggered.
- **UI primitives**: `el`/`card`/`kv`/`badge`/`statusBadge`/`watts` (null → "—"), `matrixConfidence` (`app.js:1636`), the ledger list, sticky-header CSS, filter-without-refetch technique (`matrixApplyFilter`), poll trimming (`app.js:759-772`), state survival across re-render (`state.matrix`, `app.js:595-603`).
- **Test harnesses**: the node + DOM-shim execution of real UI code (`tests/unit/test_panel_data.py:29-66`) and the Playwright e2e skip-if-absent pattern (`tests/unit/test_panel_matrix_e2e.py`). Keep both and re-point them at modules.
- **HA**: unique_id scheme `f"{entry_id}_{device_id}_{key}"` (`sensor.py:291`); the entity-id stability transcription test (`tests/integration/test_entity_id_stability.py`); `BINDABLE_KEYS` split of physical vs provenance entities (`entity_values.py:253`); the `energy` held-total logic; `entity_migration.py` for any key rename.

## 4. Proposed work packages

`addon/ui/app.js` (5,490 lines) and its tests are the hot spot. ~53 test call sites slice it by string markers (`script.index("function X(")`), and its name is hard-coded in 6 places. So **E0 must land first and alone**. Suggested split: native ES modules (`<script type="module" src="ui/main.js">`). They are allowed by CSP `script-src 'self'`, need no build step, resolve relative imports under the ingress prefix, and node can `import()` them in tests with a DOM shim on `globalThis`. File names must be flat (`ui/<name>.js`) because the gateway route is `/ui/{asset}` (single path segment, `addon/gateway.py:575`).

## 5. Traps and constraints

- **T1 Ingress paths.** All UI requests must stay relative to `document.baseURI` (`app.js:30-35`). ES-module `import './x.js'` resolves against the module URL `…/ui/main.js`, which is fine under `/api/hassio_ingress/<token>/`. Never use absolute `/ui/...`. The 401-reload-once logic (ADR-0032, `app.js:44-86`) must stay in exactly one module.
- **T2 Gateway serving.** `/ui/{asset}` takes one path segment and a fixed allowlist (`addon/gateway.py:189-201, 442-468`). New modules need allowlisting (or a safe pattern). Subdirectories will 404. Assets are `Cache-Control: no-store`, so every module is re-fetched on each load through ingress. Keep the module count modest (~12). Assets are gated on the ingress peer (`_peer_trusted`).
- **T3 CSP.** `script-src 'self'` (no inline, no eval); `style-src 'unsafe-inline'` (inline style attributes are allowed). `<script type="module">` from self is fine. `check_panel.py` check 6 bans `eval`/`new Function`/`document.write`.
- **T4 `check_panel` gate.** It hard-codes `REQUIRED = (index.html, app.css, app.js, mark.svg)` and scans only those files. `STRINGS` is parsed from `app.js` with the regex `const STRINGS = \{(.*?)\n  \};` at 2-space indentation, which changes if the block moves to module top level. The retired "dedicat" vocabulary scan and the `dedicated_device: 'Branch CT'` alias line must survive the split. The file list also appears in `scripts/package_addon.sh:115`, `scripts/validate_addon.sh:85-88,471`, `tests/integration/test_release_pipeline.py:126`, `tests/unit/test_panel.py:101,169,185,312-333`. `node --check` on an ES module with `import` fails without `--input-type=module`/`.mjs`. If `.mjs` is used, add it to `ASSET_TYPES`.
- **T5 Slice-based tests.** `test_panel.py` (36 sites) and `test_panel_data.py` (17 sites) evaluate substrings of `app.js` between function-name markers (e.g. `_SLICE_START = "const el = ..."`, `_SLICE_END = "function systemCard("`). Any reorder or rename breaks them. E0 must convert them to module imports in the same change.
- **T6 Perf / bulk reads.** Today `GET /mapping` re-reads every `device_ct_association` row, including superseded ones (no `valid_to` filter), with full `evidence_json`, under the **writer lock** (`database.py:958`). It also bulk-reads models and fetches the HA registry. Commit `53c3651` exists because this was polled every 8 s. The new path must read the materialised view on a `_reader()` connection, expose `mapping_version` for 304s, and never put the matrix in the 8 s poll. UI DOM: a dense 500×100 grid is 50k cells. Render sparse cells, collapse groups by default, and consider row windowing.
- **T7 Contract major bump.** Engine and HA integration both pin `CONTRACT_VERSION = "2.4.0"` (`contracts.py:32`, `custom_components/wattmosaic/const.py:31`). `api_client._check_contract` (`api_client.py:190-209`) raises `EngineContractMismatch` on a major mismatch. Add-on and HACS integration are updated independently, so a 3.0.0 engine with a 2.x integration disables HA entities. Release them together and document min versions and rollback (HB §16 items 8–9).
- **T8 HA entity stability.** unique_id = `{entry_id}_{device_id}_{key}` (`sensor.py:291`). If canonical Physical Device ids replace `dev_*`/`dev_auto_*` ids, every per-device unique_id changes and long-term statistics are orphaned (`test_entity_id_stability.py` explains the mechanism). Device ids must stay stable or migrate through `entity_migration.py`. Changing `power` from 0 to `None` is safe for statistics (it creates gaps), but changing unit, device_class or state_class is not. New enum sensors must list every option, or HA logs invalid-state errors.
- **T9 Energy.** `energy` is engine-owned `total_increasing`. Under ALLOCATED/UNKNOWN the engine must not integrate fabricated power into `energy_kwh`. That is a joint-inference/learning concern, but it shows up here.
- **T10 Determinism vs persistence.** The existing tests assert byte-identical projections. Persisted cells carry `updated_at`. Keep a pure `materialise_cells` for replay (acceptance 19) and test the storage separately.
- **T11 UI CSS bug.** `app.css:1011` gives body-row `th.matrix-pivot-device` `top:30px` sticky, so all row headers pin vertically. Fix it in E4.
- **T12 `_is_ct_auto_circuit` heuristics** (`mapping.py:231-266`) and the config-marker lists duplicated in `facade.py:159-170`: delete them once rows come from a canonical device registry. Do not carry them forward.
- **T13** `reconcile_topology_change` compares *string* topology tokens for cells against *int* versions for records (`mapping.py:904-918`). The v3 contract should use one version type.

## 6. Open questions for the product owner

1. **Endpoint break:** replace `/mapping` in place with the v3 shape, or add `/matrix` and delete `/mapping` in the same release? Is there any external consumer of `/mapping`?
2. **Row population:** which HA devices may appear as rows? Only devices with an electrical relation or a declared/auto placement, or every HA registry device (the current behaviour)? How should an HA device be linked to an engine Physical Device when both exist?
3. **Room grouping:** may the engine read HA `area_id` for display grouping (§9.3/§19.2)? Auto-placement deliberately ignores areas for membership; display-only use would be new.
4. **Smart plugs / device endpoints as Reader columns** (HB "Direct Devices / PLUG-TV"): should plug power entities become Measurement Endpoints with their own column? Today they are device-owned and not CTChannels. If so, where do unlocated plugs sit (the HB says an "unassigned measurement group")?
5. **HA presentation of non-identifiable devices:** should the power sensor be `unknown`, or `unknown` plus attributes? Should WattMosaic create HA group-power entities for device groups (new synthetic HA devices)? Accept the break where existing 0 W history turns into gaps?
6. **Default cell content:** show watts by default, or observability/status by default with watts on demand? Which of the 7 confidence components appear in the compact cell?
7. **History retention** for `mapping_cell_versions`, and how far back the UI's historical (`at=`) matrix should go.
8. **Debug features:** keep the current debug trace, raw-id toggle, source ledger and identifiability cards as a "diagnostic mode" on the matrix page, or move them to Diagnostics?
9. **Topology vs Matrix tabs:** keep both (topology = structure, matrix = attribution), or make the matrix header the topology editor's entry point?
10. **Release coupling:** is a synchronized add-on + HACS release acceptable for the contract 3.0 break, or is a one-release dual-shape period required (HB §16 discourages long compatibility layers)?
