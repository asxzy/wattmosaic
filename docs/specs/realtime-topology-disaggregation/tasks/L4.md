# L4 — Learning observation intake and quality gate v2

**Wave:** 4 · **Depends on:** L1, S18, K04 · **Size:** M · **Design:** §9 (gate) · **Analysis:** `analysis/F-…` C1, §1 rows §13.1, WP-F4

## Objective
Learning consumes **device-attributed** observations built from CONFIRMED event-group inferences, not whole-circuit power (`learning/sample_collector.py:327-367`). The ordered gate adds identifiability, unknown-load ambiguity, the relationship lifecycle, independence and model consistency. Rejections are kept with reasons.

## Owns
- `engine/wattmosaic_engine/learning/sample_collector.py` → becomes `learning/observations.py` (keep the old module until Z2)
- `engine/wattmosaic_engine/learning/sample_filter.py`, `learning/thresholds.py`, `learning/reporting.py`
- `engine/wattmosaic_engine/learning/pipeline.py` (intake half)
- new `tests/unit/test_observations.py`, `tests/unit/test_learning_gate_v2.py`

## Steps
1. `build_observations(result: JointInferenceResult, group: EventGroup, versions) -> list[LearningObservation]`:
   - one per (subject, endpoint) with a delta;
   - `level_w` only for a confirmed single-subject endpoint;
   - deterministic ids.
2. The gate follows the order in design §9. Non-identifiable subjects feed the **group** only (no per-device update; AT-07 learning side). A relationship in SUSPECTED_CHANGE is held as `provisional`. The learning gate uses T4's `edges_confirmed_for(subject_id)`, not the aggregate topology flag.
3. Keep the ordered deterministic rejection ledger (`_CHECK_ORDER`, `SampleDecision`). Add the new reasons. `LearningAccounting` reports per reason.
4. Persist through S18 (`put_observation`, idempotent).

## Tests
- Every new rejection reason is reachable.
- The 250 W group scenario produces zero per-device observations.
- The same group replayed twice gives the same observation ids and no duplicates.
- A relationship in SUSPECTED_CHANGE gives `provisional`.
- A delta-basis observation on a shared circuit carries only the device's ΔP, not the row's level.
