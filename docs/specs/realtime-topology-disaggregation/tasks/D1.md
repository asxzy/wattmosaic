# D1 — Version lifecycle service

**Wave:** 3 · **Depends on:** S13, S14, S15 · **Size:** M · **Decisions:** DEC-09 · **Interfaces:** §7 · **Analysis:** `analysis/A-…` C2, C8, WP-A3

## Objective
One service owns the independent topology and mapping lifecycles (rule 20):
- the current and as-of `VersionTriple`;
- configuration-event recording;
- SUSPECTED_CHANGE marking;
- propose/promote/rollback, always append-only.

The model-set id comes from L1's registry. This service only assembles the triple.

## Owns
- new `engine/wattmosaic_engine/versioning/__init__.py`, `versioning/service.py`
- new `tests/unit/test_version_service.py`

## Steps
1. Implement the `VersionService` Protocol (`interfaces.md` §7) over the S14 and S15 repositories.
2. `propose_*` creates a `candidate` version whose parent is the active one. `promote_*` sets it active and marks the previous version superseded, in one transaction. `rollback` creates a **new** version that copies the target's edge set with `rollback_of` and never reactivates rows in place.
3. `as_of(t)` comes from the version activation timestamps. The topology and mapping views are cached per version id.
4. `mark_suspected` sets lifecycles to SUSPECTED_CHANGE and appends edge-history rows.

## Tests
- The plug-relocation scenario: the mapping version bumps and the topology version does not. A reader move bumps both.
- `as_of` an old t returns the old triple.
- Rollback appends.
- Concurrency: two proposals in flight → the second promote fails clearly (optimistic check on the parent version).
- Views are immutable.
