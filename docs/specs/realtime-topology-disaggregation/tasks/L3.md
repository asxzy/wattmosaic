# L3 — Dynamic, Response-Kernel and Component-sum model classes

**Wave:** 3 · **Depends on:** L1 · **Size:** L · **Decisions:** DEC-07 · **Design:** §9 · **Analysis:** `analysis/F-…` C4, WP-F3

## Objective
- **Dynamic:** several hidden operating states under one HA state, with transitions and durations.
- **Response kernel:** h(τ | transition, attrs) with startup/active/steady/shutdown/standby phases. It exposes `expected_window` for I2.
- **Component sum:** a device = Σ of user-declared Load Components, where one HA entity may drive several components with separate kernels.

## Owns
- new `engine/wattmosaic_engine/models/dynamic.py`, `models/kernel.py`, `models/components.py`
- `engine/wattmosaic_engine/models/segmentation.py`, `engine/wattmosaic_engine/learning/stages.py`
- new `tests/unit/test_model_dynamic.py`, `tests/unit/test_model_kernel.py`, `tests/unit/test_model_components.py`

## Steps
1. Dynamic: initialise states with the robust segmenter (`segmentation.py`), map HA states to sets of states, and keep running transition counts and duration stats. If segmentation is ambiguous, say so (`stages.py` "never claim a stage you can't distinguish").
2. Kernel: fitted from aligned FINAL event windows (P4 evidence), keyed by transition type. `expected_window(transition, attrs, tau_s)` returns (mean, sigma). The default kernel when none is learned is a declared delay step (`device_profile.py:223-227`).
3. Components: `ComponentSumSpec` references `LoadComponent` ids (K01). Each component has its own model version. HA-entity links target components (DEC-08). Delete `CompositeDeviceModel` and the `component:` note tags from the v3 path.

## Tests
- An X07 fridge cycle gives ≥ 2 states under one HA state.
- The kernel separates a lamp (0 s), an HVAC compressor (+90 s) and a blind (transient → standby).
- HVAC fan and compressor components predicted as a sum with separate delays.
- Every class round-trips through the L1 codec.
- An ambiguous segmentation yields "unknown stage", not a guess.
