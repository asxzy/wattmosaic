# V2 — Performance, real-data replay, migration rehearsal, deployment report

**Wave:** 6 · **Depends on:** V1 · **Size:** M · **Decisions:** DEC-02, 37

## Objective
Show that the system holds on real-shaped load and real data before it reaches `main`. Write the deployment report the release depends on.

## Owns
- new `docs/specs/realtime-topology-disaggregation/verification-report.md`
- new `tools/dev/perf_runtime.py`

## Steps
1. Performance (Pi-class budget, also run on CI hardware):
   - 40 readers, 500 HA entities, 30 events/s for 1 h simulated;
   - report fast-path µs per sample, event-loop latency p50/p95/p99, `/healthz` p99, background job durations, DB growth per day and the matrix 500×100 API p95 and render time.

   Gates: `/healthz` p99 < 100 ms; the fast path < 0.2 ms per sample.
2. Known limitation from Z2c: `tools/audit/replay_capture.py` currently binds the replay to the HB17 version triple. Before any real-DB replay, make it read the active topology/mapping versions (and model set) from the database being replayed.
3. Real-data replay (operator-run; never commit real data, per the CI privacy job):
   - `tools/dev/replay_nesting.py --score` on the operator's DB copy;
   - `tools/audit/replay_capture.py` through v3.

   Report scores relative to the pre-3.0 baseline recorded in X00.
3. Migration rehearsal: copy the operator's DB, then start the v3 engine and confirm the backup was created, migrations 13–25 applied, counts preserved, ids preserved and HA unique ids unchanged. Then roll back: restore the backup and start the previous add-on version, and confirm it runs. Write the procedure into the report.
4. The report states facts only, with commands and outputs, in the format of `docs/specs/load-disaggregation/16-final-verification-report.md`. Scrub hosts and paths (`tools/dev/verify.py` `_scrub`).

## Acceptance
- Gates met.
- Rehearsal passed both ways.
- The report is committed.
- The orchestrator decides the merge of `feat/realtime-v3` into `main`; that is a human decision.
